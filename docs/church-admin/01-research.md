# 교적·재정 시스템 리서치 — 디모데 대체

작성 2026-10-08 · 브랜치 `church-membership-finance-research`

목표는 지금 쓰는 **디모데 교회관리**(㈜스데반정보)를 이 웹앱 안의 **재적(교적)** · **재정** 기능으로
대체하는 것이다. 이 문서는 설계 전 리서치 결과다. 설계는 [02-registry-design.md](02-registry-design.md)(재적), `03-finance-design.md`(재정)에서 한다.

> 법규 부분은 법령 원문(국가법령정보센터, 2026-10-08 기준)을 확인해 정리한 **설계 참고 자료이지
> 법률 자문이 아니다.** `[해석 필요]` 표시는 전문가 확인이 필요한 항목이다.

---

## 0. 한눈에 보기

1. **디모데는 교적과 재정이 별개 프로그램이다.** 제공 형태는 네 가지다: Windows 설치형, 웹(V6/NEXT),
   2021년 출시한 워칭(V8), 모바일 앱 여러 개. 재정은 기본이 단식(현금주의)이고, 복식은
   별도 유료 제품이다. 전자기부금영수증 같은 기능은 **부가기능마다 연 사용료**가 따로 붙는다.
2. **데이터 이전이 이 프로젝트의 성패를 가른다.** 설치형 교적은 내부적으로 **MS SQL Server**를 쓰는 것으로
   보이고, 이 경우 백업은 `.BAK` 파일이다. 우리 교회가 **어떤 형태로, 누구 서버에서** 쓰는지에 따라
   확보 경로가 달라진다. 이것부터 확인해야 한다.
3. **국내 제품은 회계까지 내장하고, 해외 제품은 헌금 관리만 한다.** Planning Center나 Rock RMS 같은 해외 제품은
   회계를 외부 회계 프로그램에 맡긴다. 한국 교회는 예산 → 결의서 → 전표 → 결산 → 감사까지 한
   시스템에서 하길 기대한다.
4. **헌금은 개인에게 귀속돼야 한다.** 기부금영수증은 헌금자 본인 명의로만 발급된다(부부 합산 불가).
   가족(세대)은 조회·집계 단위로만 쓴다.
5. **주민등록번호는 교적에 둘 수 없다.** 처리 근거는 기부금영수증과 원천징수 관련 시행령뿐이고,
   본인 동의로는 근거가 되지 않는다. 별도 테이블에 암호화해서 두고, 영수증 업무에서만 꺼낸다.
6. **종교 정보는 민감정보이고, 교인으로 등록돼 있다는 사실 자체가 종교 정보다.** 종교단체 특례(개인정보 보호법 제58조)가
   있지만 세무 처리는 특례 밖이다. 동의 기록, 접속기록 2년 보관, 관리자 MFA를 기본으로 깔고 가는 편이 안전하다.
7. **지금 DB에 보안 구멍이 있다.** 교인 633명의 연락처·생년월일을 로그인 없이 읽을 수 있고, 가입자가
   자기 권한 등급을 관리자로 바꿀 수 있다(§6.3). 교적·재정을 올리기 전에 먼저 막아야 한다.

## 1. 디모데 — 대체할 대상

### 1.1 제품과 제공 형태

- 제작사: ㈜스데반정보 (1994 설립, 서울 종로). 1995년 교적/재정 4.0 → 2014 복식재정 → 2021 워칭 V8.
- 영문명은 *Dimode*다(dimode.co.kr). 이름이 비슷한 다른 '디모데'들과 무관하다.

| 형태 | 구조 | 원본 DB를 누가 갖나 |
|---|---|---|
| 설치형 + 교회 자체 서버 | Windows 클라이언트(.NET 3.5)가 교회 서버의 DB에 접속 | **교회** — 관리자 메뉴에서 백업 |
| 설치형 + 임대 서버 | 같은 클라이언트, '임대형 연동'으로 스데반정보 서버에 접속 | 회사 |
| 웹 (V6 / NEXT) | 교회별 서브도메인(예: `xxx.dimode.co.kr`), ASP.NET | 회사 |
| 워칭 (V8) | PC·모바일 교적 + 재정. 세팅에 1~2주 | 회사 (PC 쪽이 웹인지 설치형인지 미확인) |

- 교적과 재정은 **로그인도 따로** 한다. 웹 교적에 설치형 재정을 붙이는 식으로 섞어 쓸 수 있다.
- 앱도 여럿이다: '디모데 교회관리'(재정 담당자용), 'watching'(교적), 스마트성도앱(전 성도).
  앱이 너무 많아 교회가 구분 안내문을 따로 올릴 정도다.
- 핵심 제품 가격은 공개돼 있지 않다(전화 문의). 공개된 부가기능 가격은 이렇다.

| 부가기능 | 가격 |
|---|---|
| 전자기부금영수증 | 연 22만원(1,000명 이하) ~ 110만원 |
| 온라인행정 | 구축비 11만원 + 연 24.2만원~ |
| 종교인 회계 | 구매 88만원 + 월 2.2만원~ |

### 1.2 교적 기능

| 영역 | 내용 |
|---|---|
| 인적사항 | 교번, 이름(동명이인은 접미사로 구분, 예: '홍길동C'), 성별, 생년월일 **양/음력**, 휴대폰·집전화, **문자거부**, 이메일, 주소, 사진, 등록일, 직업·직장, 차량 2대 |
| 신앙 | **교인구분**(2~3단계, 이력 남음), 직분 + 임직일, 직책, 신급(세례 등, 세례증명서 출력), 인도자, 이전교회 |
| 가족 | **신앙세대주 + 세대주와의 관계**. 분가·합가는 세대주를 바꾸는 방식. '대가족 보기'(여러 세대 묶음), 워칭에는 5대 가계도 |
| 조직 | 교구/구역/목장/속을 **연도별 최대 4단계**로 정의. 교회학교·청년은 별도 조직. 선교회는 나이·성별 조건으로 일괄 배정 |
| 이력 탭 | 속회, 직분, 심방, 관계, 교육, 은사, 출결, 메모, 돌봄, 주소, 교인구분, **수정내역**(사용자·PC·일시·SQL) |
| 심방 | 일자, 심방자 1·2, 성경·찬송, 구분, 내용. 열람·수정 권한을 전체/담당교구/본인 작성분으로 나눔 |
| 상태 변화 | '삭제' 대신 **보류/제적**(가족 단위, 사유 입력). **영구삭제 불가, 언제든 복구**. 별세는 교인구분을 '소천'으로 변경 |
| 통계 | 교구별·성별·결혼·신급·교인구분, 등록·제적·전출입 기간별 현황, 연간 출석, 새가족·심방 월별 |
| 출력 | 교적부, 세례증명서, 교인증명서, 주소라벨, 검색결과 엑셀 |
| 검색 | 조직 트리, 이름 여러 개 동시 검색, 조건검색. **검색결과 열 구성을 저장**(개인용/공유용) |

### 1.3 재정 기능

| 영역 | 내용 |
|---|---|
| 헌금 종류 | 교회가 정의하는 트리. 예: 주일헌금 > 십일조·감사, 특별헌금 > 절기(부활·맥추·추수·성탄) |
| 주일 일괄 입력 | 날짜·예배(부)·항목을 고정하고 **[이름 → 금액 → Enter]** 반복. 바코드 라벨이면 [교번 → 금액]. 한 사람의 여러 종류를 한 줄에 입력하는 '종합헌금입력'. **계수자** 기록 |
| 특수 헌금자 | 교적에 없는 사람은 이름만으로 입력(교번 없음), 무기명은 이름을 '무명'으로 입력 |

### 1.4 디모데의 약점 = 우리가 나아질 수 있는 지점

| 디모데의 문제 | 우리 설계에서 |
|---|---|
| 헌금 합계와 전체 수입·지출 금액을 **따로 저장** → 결산 금액이 어긋나면 사용자가 '재계산' 버튼을 눌러야 함 | 합계는 원장 행에서 **계산만** 하고 따로 저장하지 않는다. 대신 기간 마감 잠금을 둔다 |
| 계정 코드를 손으로 끼워 넣음 | `parent_id` + 정렬순서로 트리를 만들고, 코드는 표시용으로만 쓴다 |
| 앱 3~5개로 분산, iOS 앱 품질 불만 | 반응형 웹앱 하나에 역할별 메뉴 |
| 시스템 암호 기본값 '1', 직책 계정 기본 ID가 이름 | Supabase Auth 개인 계정, 재정 담당자는 MFA |
| 백업 복원은 회사에 연락해야 함 | 우리 DB, 우리 백업 |
| 전자기부금영수증·온라인행정 등 부가기능마다 연 사용료 | 자체 구현 |
| 교적과 재정이 별도 프로그램, 별도 로그인 | 한 계정에 권한으로 분리 |

## 2. 데이터 이전 — 가장 먼저 풀어야 할 문제

### 2.1 경로 두 가지

**A. 엑셀 내보내기** — 어느 형태든 가능하다.
- 교적: 검색결과의 열 구성을 '전체 항목'으로 정의해서 전 교인을 내보낸다.
- 재정: 수입 검색 결과, 결산, 예산 화면에 엑셀 버튼이 있다. 회계연도 × 장부별로 반복해야 한다.
- 한계: 심방 이력, 히스토리, 기부금 발급이력이 전부 엑셀로 나오는지는 **미확인**이다(화면마다 다름).
  세대(HID) 같은 내부 키가 빠질 수 있다.

**B. 원본 DB** — 이력과 키가 다 남아 있으므로 가능하면 이쪽이 낫다.
- 설치형 교적의 공개 설치파일을 실행하지 않고 정적 분석한 결과, DB 이름 `Dimode2008`,
  `System.Data.SqlClient`, `BACKUP DATABASE … .BAK` 문자열이 나왔다 → **SQL Server 네이티브 백업**일 가능성이 매우 높다.
- 자체 서버라면 관리자 메뉴의 '데이터 백업'으로 받는다. 임대 서버·웹·워칭이라면 스데반정보에
  **전체 백업 제공을 공식 요청**해야 한다. 해지 시 원본을 넘겨주는지는 **미확인**이다.
- 받은 `.BAK`는 로컬 SQL Server(Docker)에 복원한 뒤 Postgres로 옮긴다.
- 참고: 다른 업체들(오직, 가정교회360 등)이 디모데 데이터 변환을 서비스로 하고 있다.
  즉 디모데 데이터를 다른 시스템으로 옮기는 일은 이미 여러 번 해 본 일이다.

### 2.2 원본 DB 구조 단서 (정적 분석)

| 테이블 | 짐작되는 내용 |
|---|---|
| `P` | 교인 마스터. `ID`(교번), `HID`(세대), `RANGE*`(조직 단계), `STATE1`, `RELATIVE` |
| `GROUP1` | 연도별 조직 (`YEAR`, `SECTION1~3`, `DEPTH`) |
| `ATT` | 출석. **연도별 주차 열 W1~W53의 와이드 구조** (예: `UPDATE ATT SET [W36]='O' WHERE ID=578`) |
| `PDELETE`, `STATEH`, `P_STATE_HIS` | 제적·보류, 상태 이력 |
| `JUMINLIST` | **주민번호 별도 테이블** (암호화 여부 미확인) |
| `BAPT`, `ADDR`, `PIMAGE`, `ERECEIPT`, `WRITEHISTORY`, `SMS_HISTORY` | 세례, 주소, 사진, 전자영수증, 수정이력, 문자 |

재정 프로그램과 웹/워칭의 DB 구조는 **미확인**이다.

### 2.3 이전할 때 지킬 것

- **교번과 세대 번호를 보존한다.** 헌금·출석·심방이 모두 교번으로 연결된다. 교번은 등록창을 열기만 해도
  증가하므로 결번이 많다.
- **헌금의 특수 행을 따로 매핑한다.** 교번 없음(이름만), '무명', 동명이인 접미사.
- **우리 DB의 기존 사람과 맞춘다.** `custom_users` 633명(로그인 계정 연결 228, 미연결 405)과 디모데 교인을
  이름 + 전화번호로 매칭하는 단계가 필요하다. 2026-06의 동명이인 정리(603→550) 경험을 재사용한다.
- **연도 단위 데이터가 많다.** 조직·계정과목·예산이 모두 회계연도별이다.
- **출석은 와이드 구조를 행으로 풀어서(unpivot)** 우리 출석부 구조에 맞춘다. 과거 출석을 가져올지는 별도 결정이다.
- **결산 합계는 믿지 말고 원장에서 다시 계산해 대조한다.** 디모데는 합계가 어긋날 수 있다(§1.4).
- **기부금 발급번호 연속성**을 유지한다. 5년 보관 의무가 있다(§5.2).
- **주민번호는 이전 대상에서 빼는 것을 기본으로** 하고, 꼭 필요하면 암호화 테이블로만 옮긴다.

## 3. 다른 제품에서 배울 것

### 3.1 국내 제품 (지저스온, 오직, 온맘교적, 디바인, 만나ERP, 아이처치)

공통 패턴:

1. **입력은 단식, 장부는 복식.** 수입·지출 전표만 넣으면 자동 분개해서 복식장부를 만든다.
   단식만 아는 재정부원도 쓸 수 있고, 결과는 재무상태표까지 나온다.
2. **헌금 입력이 회계 전표로 자동 연결**된다. 이 연결을 켜고 끌 수 있다.
3. **회계단위**(일반·특별)를 개수 제한 없이 만들고, 단위별로 계정과목을 따로 둔다.
4. **지출 흐름:** 결의서 → 결재라인 → 승인 시 전표 → 영수증 첨부 → 일 단위 마감 → 연도 이월.
5. **헌금 입력자 권한을 잘게 나눈다**(지저스온): 본인이 입력한 것만 조회, 주일에만 입력, 당일분만 조회 등.
6. **주보용 헌금자 명단 자동 생성.** 반대로 '헌금 무기명주의' 교회도 있어서, 이 기능은 교회 정책에 따라 켜고 끈다.

가격 참고: 지저스온·온맘교적은 월 7,700원(100명) ~ 59,000원(최고급형). 디바인 웹은 월 9,900~38,000원.
이전 비용은 교적 11만원, 헌금회계 11만원 정도다(온맘).

### 3.2 해외 제품의 데이터 모델 (Rock RMS·ChurchCRM은 소스 확인, Planning Center는 API 문서)

| 배울 점 | 출처 | 우리에게 |
|---|---|---|
| **헌금 배치**: 입력 중 → 확정 → 마감. 확정 후 다시 여는 건 별도 권한 | Rock `FinancialBatch.Status`, Planning Center commit | 주일·예배별 헌금 집계와 일마감 |
| 배치에 **통제금액**(계수 합계)을 적고 입력 합계와 맞아야 마감 | Rock `ControlAmount` | 계수표 금액과 입력 금액 대조 |
| 헌금 1건을 여러 종류로 분할 | Rock `TransactionDetail`, PC `designation` | 한 봉투에 십일조 + 감사헌금 |
| 권종(지폐·동전) 수량 기록 | ChurchCRM `pledge_denominations` | 계수표 |
| 사람 병합 후에도 헌금 이력 유지: 헌금이 사람 대신 **별칭(alias)**을 참조 | Rock `PersonAlias` | 우리 `merge_user_data` 병합 흐름과 같은 문제 |
| 무기명 헌금 = 사람 없이 입력 | PC(사람 필드 선택 사항), Rock(익명 레코드) | 무기명·미등록 헌금자 |
| 사람 상태를 **여러 축**으로: 레코드 상태(활동/비활동/대기) + 연결 상태(교인/출석자/방문자) + 비활동 사유 | Rock, Planning Center | 재적 상태 설계 |
| 하드 삭제 없음, 비활성화로 이력 보존 | Rock | 디모데와 동일 |
| **조직 관리자도 재정에는 자동 접근 못 함** | Planning Center(Giving만 예외) | 사이트 관리자 ≠ 재정 열람자 |
| 입력자(Counter)와 확정자(Bookkeeper) 분리 | Planning Center | 계수·입력·확정 직무 분리 |

반대로 따르면 안 되는 점: ChurchCRM과 Rock은 헌금을 **가족**에 귀속할 수 있다. 한국은 영수증이
개인 명의로만 나가므로 헌금 귀속은 개인이어야 한다. 그리고 Rock은 스스로 "온전한 회계 시스템은 우리의
미션이 아니다"라고 밝힌다 — 회계 부분은 국내 제품을 참고해야 한다.

## 4. 한국 교회 재정 관행

> 우리 교회는 **대한예수교장로회 합동** 소속이다(`/about`). 아래 교단 규정 사례는 대부분 **예장통합**
> 자료라서, 합동 헌법·재정 규정과 교회 자체 정관으로 다시 확인해야 한다.

### 4.1 흐름

| 단계 | 관행 (예장통합 「교회 회계 기준」 등) |
|---|---|
| 회계연도 | 1/1 ~ 12/31 |
| 예산 편성 | 부서 사업계획 → 예산요구서 → 예산위원회 → 제직회 → **공동의회 승인**. 추경도 공동의회 |

| 보고 | **매월 예산집행수지계산서를 제직회에 보고**. 연말 결산은 예산 대비 실적·증감 형식 |
| 감사 | 당회·제직·평신도 대표가 중간감사와 결산감사. 의견은 적정/한정/부적정/의견거절 |
| 보존 | 장부 5년(통합 기준), 교회에 따라 10년. 재무제표는 영구 |

### 4.2 헌금 계수 내부통제

- 계수는 **2인 이상, 서로 가족이 아닌 사람**이 한다. 계수팀을 교대로 운영한다.
- 집계표를 2부 이상 만들어 책임자가 서명한다. **당일 또는 익일 입금**한다.
- **집행, 기록, 감독을 분리**한다(기윤실·교회재정건강성운동 원칙).
- 개인별 헌금 내역은 법령상 필요할 때 외에는 공개하지 않는 교회가 많다.

### 4.3 단식이냐 복식이냐

- 전국 통계는 없다. 전문가들은 **연 예산 5억 미만이면 단식도 괜찮고, 넘으면 복식을 권한다.**
- 공인된 교회회계기준은 없다. 대안으로 공익법인회계기준의 원리가 제안된다.
- 결산서는 **기능별**(예배·선교·교육·구제)과 **속성별**(인건비·운영비) 분류를 함께 보여야 한다는 권고가 있다.

## 6. 현재 시스템에서 출발점

### 6.1 재사용할 수 있는 것

- **사람 키 `custom_users.id`** — 출석 계열이 이미 이 키를 쓴다. 미가입 교인을 placeholder로 두고 가입 시
  병합하는 흐름(`merge_user_data`)도 그대로 쓸 수 있다.
- **권한 패턴** — 기능별 지정 테이블(`attendance_managers`, `education_report_editors`, `export_users` 등)과
  `app_is_*` / `app_can_*` 헬퍼, 그리고 이를 쓰는 RLS 정책. `registry_managers` + `app_can_access_registry()` 식으로 복제하면 된다.
- **감사 로그** — 새 테이블에 `audit_row()` 트리거 한 줄을 붙이고 `src/lib/audit.ts`에 라벨을 추가하면 된다.
- **CSV 내보내기** — `src/lib/csv.ts`(BOM 포함, 엑셀 호환), 1000행 제한을 넘는 `fetchAll()`.
- **조직** — `communities`(3) / `small_groups`(29) / `small_group_members`(536)를 교적의 교구·구역(목장)으로 쓸 수 있다.
- **인적사항 일부** — 이름, 성별, 생년월일, 전화, 직분(`office`)은 이미 있다.

### 6.2 부딪힐 제약

| 제약 | 내용 |
|---|---|
| 모든 데이터 접근이 브라우저에서 이뤄진다 | anon 키 + 사용자 세션으로 직접 조회한다. 서버가 사용자 대신 쿼리하는 구조(`hooks.server.ts`, `@supabase/ssr`)가 없고, 서비스 롤 키도 쓰지 않는다. **권한은 전적으로 RLS와 RPC 가드에 달려 있다.** 주민번호 암호화 키를 브라우저에 둘 수 없으니, 그 부분은 서버(또는 Edge Function) 경로가 필요하다 |
| 교적 필드가 없다 | 주소, 세대·가족관계, 등록일, 세례·입교, 임직일, 이전교회, 재적 상태, 비고 |
| 의미가 겹치는 컬럼 | `custom_users.active` = 가입 여부, `small_group_members.active` = 그 그룹 명단에서 제외. `office`에 직분과 아동 연령 구분(유치·초등 등)이 섞여 있다. `member` 컬럼은 의미 불명. 재적 상태를 기존 `active`에 얹으면 병합·RLS·통계가 깨진다 |
| 병합 트리거 | `merge_user_data`는 4개 관계만 옮기고 placeholder를 지운다. **새 교적·재정 테이블이 사람을 참조하면 이관 목록에 반드시 추가해야 한다.** 헌금은 CASCADE가 아니라 RESTRICT + 이관 |
| 감사 로그 | fail-open(실패하면 조용히 누락), 변경 전후 행 전체를 복제해서 민감정보가 로그로 퍼진다(주차 기능은 이 때문에 감사 대상에서 뺐다), **조회는 기록하지 않는다.** 재정에는 별도 설계가 필요하다 |
| 스키마가 저장소에 없다 | `supabase/` 폴더가 없고 DB의 마이그레이션 기록(29건)에만 남아 있다. 이번 기능부터 마이그레이션 SQL을 저장소에 두는 것을 검토할 만하다 |
| 출석 재적의 시점 이력 | 출석부의 "그 주의 재적"(가입·이탈 이력)은 보류 상태다(`docs/attendance-stats.md`). 교적의 등록·이동 이력과 함께 설계하면 같이 풀린다 |
| 교육부서는 사람과 연결돼 있지 않다 | 부서 목록은 코드에 고정된 5개이고, 보고서의 재적·출석은 손으로 넣은 숫자다 |

### 6.3 먼저 막아야 할 보안 문제 (DB 정책을 직접 확인함)

1. **`custom_users`를 누구나 읽을 수 있다.** SELECT 정책 `Enable read access for all users`가 `qual = true`,
   대상 role `public`이다. 사이트에 들어 있는 공개 키만으로 **로그인 없이 633명의 전화번호·생년월일·이메일·성별**을
   조회할 수 있다. 교적 필드를 이 테이블에 추가하면 그대로 공개된다.
2. **자기 권한 등급을 올릴 수 있다.** UPDATE 정책 `Allow updates based on active status`는
   `(active = false) OR (active = true AND auth.uid() = auth_id)`이고, `role` 컬럼을 막는 컬럼 권한이나 트리거가 없다.
   본인 행의 `role`을 관리자로 바꾸는 것이 정책상 허용된다. 또 로그인한 사용자 누구나 **미가입 교인 placeholder(324행)를
   수정**할 수 있다. 여기에는 `auth_id`를 바꾸는 것도 포함된다.
3. 실제로 값을 바꿔 보지는 않았다(읽기 전용 확인). 앱의 사람 검색 기능이 1번 정책에 기대고 있어서,
   막을 때는 공개용 뷰나 RPC를 함께 만들어야 한다.

→ **2026-10-08 조치 완료** (브랜치 `fix-custom-users-rls`, 마이그레이션 `custom_users_lockdown`).
  비로그인은 게시글 작성자의 이름·직분·사진만, 로그인 사용자는 본인·담당 범위·정보공개 교인만 보인다.
  role·auth_id·member·active 변경은 트리거로 막았고, 계정 삭제 함수와 메시지·게시글 사칭도 함께 막았다.
  **남은 과제:** 앱이 `select('*')`를 쓰기 때문에 로그인 사용자의 *컬럼* 권한은 아직 좁히지 못했다
  (보이는 행의 전화·이메일은 보인다). 앱 업데이트 후 2단계로 처리한다. 교적 필드는 처음부터 별도 테이블에 둔다.

## 7. 리서치가 설계에 주는 원칙

1. 교적의 사람은 `custom_users`를 그대로 쓰되, **민감한 교적 필드는 별도 테이블**(담당자 전용 RLS)에 둔다.
2. **세대(가족)는 사람과 분리**한다. '신앙세대주 + 관계' 방식을 따르고, 교인 아닌 가족원도 기록할 수 있게 한다.
3. **재적 상태는 이력 테이블**로 둔다(등록·전입·이명·제적·별세·보류·복적, 사유·일자·처리자). 영구 삭제는 없다.
4. 조직과 계정과목은 **연도별 트리**로 만들고, 코드에 의미를 싣지 않는다.
5. **헌금은 개인에게 귀속**된다. 무기명·미등록 헌금자를 허용하고, 1건을 여러 종류로 분할할 수 있게 한다.
6. **헌금 배치**(예배·일자)에 통제금액, 계수자 2인, 입력 중 → 확정 → 마감 상태를 둔다.
7. **합계는 저장하지 않고 원장에서 계산**한다. 기간 마감 잠금을 두고, 정정은 수정 전표로만 한다.
8. **입력은 단식처럼 쉽게 하되, 내부는 복식으로 쌓을지**는 결정이 필요하다(교회 재정 규모에 달림).
9. **재정 권한은 사이트 관리자와 분리**한다: 입력자 / 확정자 / 재정부장 / 감사(읽기 전용) / 영수증 발급자.
10. **주민번호는 암호화 + 서버 경로**로만 처리하고, 교적·재정 데이터는 조회까지 접속기록을 남긴다.
11. 기존 보안 구멍(§6.3)을 먼저 막는다.
